### **\[BREACH-001\]: LETHAL**

**\[MODULE & LOCATION\]:** **`kernel\_rust\_v813.rs :: polydim\_rust\_frechet\_betti\_filter :: línea del quórum`**  
**\[MATHEMATICAL / PHYSICAL ROOT CAUSE\]:**  
El manifiesto V813 documenta explícitamente el fix C4: *"Quórum BFT estricto: **`3a \> 2n`** (antes **`\>=`**, que para n=3f admite 2f)."* Sin embargo, el código DESPLEGADO contiene la fórmula VIEJA **`\>=`**, no la nueva **`\>`**:

rust


let quorum\_ok = (active as u64) \* 3 \>= (2 \* n as u64); // ← BUG: usa \>= en vez de \>


**Análisis matemático del fallo BFT:**  
Para **`n = 3f`** (configuración admitida por el código actual), el umbral BFT estándar requiere **`a ≥ 2f+1`** (quorum que intersecta cualquier otro quorum en al menos **`f+1`** honestos). La fórmula **`3a ≥ 2n`** para **`n = 3f`** da **`a ≥ 2f`**, que **NO** garantiza intersección de **`f+1`** honestos entre dos quorums disjuntos. Un adversario bizantino con **`f`** nodos puede coludir con **`f`** honestos equivocados para producir dos certificaciones contradictorias.

**\[DEGENERATIVE SCENARIO\]:**  
**`n = 15`** nodos, **`active = 10`**, **`rejected = 5`** (33.33% bizantinos).

- Con **`\>=`**: **`3\*10 = 30 ≥ 30 = true`** → **CERTIFICA INCORRECTAMENTE**.

- Con **`\>`**: **`3\*10 = 30 \> 30 = false`** → rechaza correctamente.

El test V813 **`test\_rust\_frechet\_betti\_filter`** (TEST 6) **espera** **`is\_consensus\_certified == True`** con **`n=15, active=10`**, es decir, espera el comportamiento BUG. El test y el código están sincronizados en el BUG, no en el fix documentado.

### **\[BREACH-002\]: LETHAL**

**\[MODULE & LOCATION\]:** **`kernel\_cpp\_v813.cpp :: polydim\_stiefel\_optimize :: bucle iterativo, línea `**std::vector\<double\> Z(D \* K)\`\`

**\[MATHEMATICAL / PHYSICAL ROOT CAUSE\]:**  
El mandato explícito del Bulldog: *"Any heap allocation inside inner loops or per-thread vector instantiation is an OOM FATAL VETO."* El solver Stiefel ejecuta **alocación heap de `D\*K\*8` bytes por iteración** dentro del bucle de optimización:

cpp


for (iter = 0; iter \< max\_iters; ++iter) \{

...

if (options-\>retraction\_type == POLYDIM\_RETRACTION\_CAYLEY\_SMW) \{

std::vector\<double\> Z(D \* K); // ← ALOCACIÓN POR ITERACIÓN

...

\}

...

std::vector\<double\> Gram(K \* K, 0.0); // ← ALOCACIÓN POR ITERACIÓN

\}


A **`D = 10^7, K = 64`**: **`Z`** pesa **`5.12 GB`** por iteración. Con **`max\_iterations = 100`**, se alocate+liberate 512 GB acumulados. Esto causa:

1. Fragmentación heap catastrófica.

2. OOM en sistemas \< 16 GB RAM (solo **`X + G + Z`** ya son 15.36 GB).

3. Latencia de **`mmap`**/**`brk`** syscalls en hot path.

Adicionalmente, **`G`** es alocate una sola vez pero pesa **`D\*K\*8 = 5.12 GB`** a **`D=10^7`** — el solver entero consume ~15 GB residentes solo en buffers principales.

**\[DEGENERATIVE SCENARIO\]:**  
**`D = 10^7, K = 64, max\_iterations = 20, retraction\_type = CAYLEY\_SMW`**. En un host con 32 GB RAM:

- **`X`** (input): 5.12 GB

- **`G`** (gradiente): 5.12 GB

- **`Z`** (per-iter): 5.12 GB × 20 iteraciones (fragmentación)
